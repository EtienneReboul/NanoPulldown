# Pair specs — `configs/pairs.parquet` + `configs/curated_domains.yaml`

Every pair a run folds (its config's `pairs_file:`, else `pairs:` list) is one
row of `configs/pairs.parquet`, generated by `nanopulldown.inputs.expand` from the
run config's `inputs:` (see `nanopulldown.inputs.resolve`), or from
`configs/baits.txt` x `configs/preys.txt` without one (AlphaPulldown's
bait-file x prey-file combinatorial convention). Re-running it only ADDS new pairs; it
never rewrites existing rows. The table is reproducible, so it is gitignored.
Every column is documented in the file's own schema metadata (Data Wrangler,
`pyarrow.parquet.read_schema`, or `nanopulldown.core.io.read_schema_metadata`).

| column                          | type                                       | meaning                                                       |
| ------------------------------- | ------------------------------------------ | ------------------------------------------------------------- |
| `pair`                          | `string`                                   | `<bait>__<prey>`, the `pairs:` entry                          |
| `bait_uniprot` / `prey_uniprot` | `string`                                   | UniProt accession                                             |
| `bait_copies` / `prey_copies`   | `int32`                                    | number of chains (AlphaPulldown `ID:N`)                       |
| `bait_regions` / `prey_regions` | `list<list<int32>>`, nullable              | `[[start, stop], ...]`, 1-based inclusive; null = full length |
| `chains`                        | `list<struct<id, name, role, sequence>>`   | ESMFold2 input order; ids A, B, C... bait copies then prey    |
| `bait_chains` / `prey_chains`   | `list<string>`                             | chain ids of each side                                        |
| `n_tokens`                      | `int32`                                    | total residues ESMFold2 folds (vs `esmfold2.max_tokens`)      |
| `bait_fragment` / `prey_fragment` | `string`, nullable                       | fragment mode: the region's domain name(s); null otherwise    |

Schema `pairs/2` adds the two `*_fragment` columns. Tables written as
`pairs/1` load with them null. Fragment names are display only: they are left
out of the spec digest, so naming a fragment never re-folds a pair. In fragment
mode, `nanopulldown.inputs.expand` also writes `configs/fragments_<run>.parquet`,
with one row per fragment: accession, role, spec, fragment, start/end in
full-length numbering, length, source (interpro | override | full_length |
as_given), and the merged domain names. Hand-picked fragments go in
`configs/fragment_domains.yaml` (`{accession: [{name, start, end}]}`).

Protein-protein only: no RNA/DNA/ligand chains.

Scripts never read the table directly: `nanopulldown.core.specs.load_pair(pair)`
returns the spec as a dict (`name`, `bait`/`prey` `{uniprot, copies, regions,
fragment}`, `sequences` = the chains, `bait_chains`, `prey_chains`,
`annotation_reviewed`, `domains`), with the curated domains below merged in.

## Curated domains — `configs/curated_domains.yaml` (hand-edited, tracked)

Only pairs you have curated appear here. Preprocessing writes a proposal to
`data/annotation/<pair>/annotation.yaml`: InterPro's representative domain set,
plus any InterPro domain entries that set leaves uncovered, each region named
after its best-matching InterPro domain entry (see
`nanopulldown.annotate.merge`). The file's `interpro:` block holds the full
evidence (family, every InterPro entry with its member databases, unintegrated
signatures, MobiDB-lite / coils / signal peptide / TM tracks) that the domain
figure draws. Copy its `domains:` block under the
pair's name and set `annotation_reviewed: true`; report figures then use it
instead of the proposal. Curation is informational only and never gates
folding. Editing an entry reruns just that pair's figures: rules carry a digest
of each pair's spec and curation as `params`.

```yaml
example_toy__example_toy:
  annotation_reviewed: true
  # Per chain id, an ordered list of segments. `kind` is one of:
  # domain | linker | disordered | morf. 1-based, inclusive. "linker" is
  # always a human call -- neither AIUPred track outputs it directly.
  domains:
    A:
      - {name: ubiquitin_fold, start: 1,  end: 72, kind: domain}
      - {name: LRGG_tail,      start: 73, end: 76, kind: disordered}
    B:
      - {name: ubiquitin_fold, start: 1,  end: 72, kind: domain}
      - {name: LRGG_tail,      start: 73, end: 76, kind: disordered}
```

`example_toy__example_toy` (a ubiquitin homodimer smoke test) is kept as the
worked reference for a curated entry.

## Display names — `configs/proteins.parquet` + `configs/protein_names.yaml`

Pairs, paths and tables stay keyed by UniProt accession. The reports label
proteins with names instead, from `configs/proteins.parquet`: one row per
accession, written by `nanopulldown.inputs.expand`. Use
`nanopulldown inputs uniprot --backfill` for pairs expanded before the table
existed. Each row holds UniProt metadata (protein name, gene, synonyms, ordered
locus, organism, length, Swiss-Prot flag, function, subcellular location,
release) plus two resolved names:

| name         | used for                         | first available of                                                                                     |
| ------------ | -------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `short_name` | axes, titles, pair labels        | gene name, input-source name (`name_column`), gene-like protein name, AGI locus (`AT3G43700`), accession |
| `long_name`  | subtitles, table column, tooltips | protein name (recommended, else submitted); placeholders such as "Uncharacterized protein" count as missing |

When several accessions resolve to the same short name, ` (<accession>)` is
appended. The exception is when exactly one of them is Swiss-Prot: that entry
keeps the plain name. UniProt metadata is cached per accession in
`data/uniprot_meta/`; delete that directory to refresh names after a UniProt
release.

`configs/protein_names.yaml` is tracked and hand-edited. It overrides either
name per accession, for a name the field uses that UniProt does not:

```yaml
Q9LMA8: {short: JAZ1}     # UniProt primary gene name: TIFY10A
```

## Run inputs — `configs/inputs_<run>.parquet`

There is one row per (accession, role) for the run named by `run_name`
(default `main`). `sources` lists the config `inputs:` sources that selected
the protein. Each `keep_columns` entry of an `ipms:` source adds a
`<source>_<column>` column (e.g. `pxd013906_logfc`). The controls
(`nanopulldown.inputs.controls`) add their tags to `sources`: `known` for the baits'
known direct partners, `decoy` for the decoy set. Every known partner of the
baits in the table, whatever its tier, carries `known_tier` (best of
`curated`, `high`, `medium`, `low`), `known_tier_of` (`<bait>:<tier>;...`),
`known_miscore` (MIscore over every database, 0-1), `known_intact_miscore`
(IntAct's own, empty for BioGRID-only partners or a format-2 snapshot),
`known_databases` (e.g. `biogrid;intact;string`, `curated` for the hand list),
`known_n_databases`, `known_string_score` (0-1000), `known_string_escore` /
`_dscore` / `_tscore` (STRING experiments / curated databases / text-mining,
0-1000), `known_direct_databases`, `known_direct_methods` (e.g. `two
hybrid`), `known_n_direct_publications`, `known_curated_pmids`,
`known_curated_note` and `known_direct_of` (the baits the partner is a
positive control for: tier >= `controls.positives.min_tier`). The results
table joins these values in for the prey.

The interactor lookup snapshots every evidence group to
`data/interactors/interactors_<run>.tsv`: one row per (query, partner,
database, detection method, interaction type), with the evidence count,
PubMed ids and `confidence` (IntAct's `intact-miscore:`, or STRING's
`escore:|dscore:|tscore:`; empty in format-2 snapshots). A `.json` beside it holds the settings, per-database counts,
failed calls and date. Partners are current primary UniProt accessions, so
the same protein counts once however each database names it. The decoys
are listed in `configs/decoys_<run>.txt`. Their provenance is in
`data/decoys/decoys_<run>.parquet`: fragment, domains, length, Cys+His
fraction, matching stratum, UniProt name and location. In fragment mode they
appear in `configs/fragments_<run>.parquet` with source `decoy`.
